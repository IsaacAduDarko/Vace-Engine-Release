ABI and types

Reference material for the VACE script ABI and the data types the Script API exposes. Most users never need this page directly. It matters when you write your own tooling, debug a script that fails to load, or want to understand why a new engine feature does not break existing scripts.

You are probably looking for the scripting reference

If you are writing gameplay scripts, the API itself is documented in the Script API reference. This page covers the underlying contract, not the calls you make day to day.

ABI version

The current ABI is v7. A compiled script reports its ABI version by returning 7u from the exported vace_script_abi() function. The engine checks this value when it loads a script DLL and refuses to load a script built against an incompatible ABI.

std::uint32_t vace_script_abi()

If you see a "script ABI mismatch" error in the editor console, the script DLL was built against an older ABI version. Rebuild the project; the current build pipeline always emits the current ABI number.

Versioning rules

VACE_ScriptContext is the function-pointer table the runtime installs into a script before OnCreate fires. Every method in the Script API is a thin wrapper over one entry in that table.

The table is append-only. Two consequences:

  • New features do not bump the version. When a new engine feature adds a function pointer, it goes at the end of the table. An old script reads the table's size field, sees a shorter struct than the engine provides, and simply stops reading. A new script reads the tail. Audio, UI, animation, physics, IK, particles, and gamepads were all added without bumping the ABI.
  • Breaking changes bump the version. Removing a function, changing a signature, or changing the meaning of an existing entry requires a new ABI number. Scripts built against the old ABI then fail the check at load time instead of misbehaving silently.
In practice

A script you build today against ABI v7 will keep working across every engine update that does not bump the ABI. When the ABI does bump, you get a clear load-time error and a rebuild fixes it.

Field injection

When the engine loads a script instance, the sequence is:

  1. Construct the script instance
  2. Install the ABI context
  3. Apply saved inspector field values
  4. Call vace_script_create_hook, which invokes OnCreate

The order means OnCreate always sees the saved inspector values (when inspector field persistence is finished; see the note on inspector fields for the current limitation).

Thread safety

All ABI calls are safe to make from OnCreate, OnUpdate, and OnDestroy. They are also safe to make from any function those hooks call directly.

Do not spawn your own threads and call into the ABI context from them. The engine serializes script execution on a single thread, and calling into the context from a different thread is undefined behavior.

Types and enums

The Script API uses a small set of POD structs and enums for values that cross the script boundary. Their field layouts are stable within an ABI version.

ScriptRaycastHit

Returned by Raycast and Raycast2D.

VACE_ScriptFieldValueType

Type tag used for values passed through the ABI when the engine applies saved inspector values. It is an internal detail of the field injection process and normally does not need to be referenced by script code.

When to rebuild

Rebuild your project (or press Play, which rebuilds automatically) after changing any of the following:

  • Any .cpp file in the project's scripts folder
  • The engine installation itself, if you update VACE
  • The compiler path or version in the Project Manager's Settings tab

If the editor reports a script ABI mismatch, rebuilding fixes it. If the editor reports a link error, the compiler path is probably wrong; see Project Manager > Settings.
